# 稳定单入口与故障驱动切换设计

> 状态：已实施（2026-08-13）
>
> 本文替代旧的“RTT/抖动触发预热切换”设计。保留文件名是为了兼容已有文档链接。
>
> 核心原则：健康时只探测和更新评分，不切换；只有主连接断线，或同一入口的 MUX 在 60 秒内连续发生两次 M1/M4，才切换到预排序备用入口。

## 1. 最终行为

### 1.1 健康运行

- 持续探测全部入口并更新历史、可靠性等级和延迟风险。
- 当前主连接和当前 MUX 入口保持粘滞，评分变化不触发迁移。
- 不执行 `Idle -> Preheating -> Ready -> Draining` 质量切换状态机。
- 一个 MUX generation 只绑定一个入口；其全部 carrier 都强制使用该入口。
- `hot-switch.channels-per-entry` 不再将 carrier 分散到多个入口。

这样可避免 RTT 毛刺、评分排名变化和跨入口时延差导致的频繁切换、乱序及卡顿。

### 1.2 主连接断线

1. 将刚失败的入口按 `probe.ttl-seconds` 临时惩罚。
2. 直接读取后台已经维护的入口排序，不等待新的完整探测周期。
3. 第一次故障切换立即开始，不再固定等待 5 秒。
4. 后续失败采用 `0ms -> 250ms -> 1s -> 2s -> 最多 5s` 退避。
5. 当前惩罚入口不会被粘滞逻辑重新选中；选择可用排序中的第一名。

只建立一个 PPP 主会话，不并发执行多个相同 GUID 的 PPP 主握手。

### 1.3 MUX M1/M4

MUX 显式记录以下终止原因：

- `M1`：不可缓冲的数据缺口或数据缺口超时；
- `M4`：NACK 重传次数耗尽。

新客户端和新服务端会在关闭前通过 `cmd_mux_rebuild` 尽力通知对端，使发起端和接收端都能识别 M1/M4，而不是把它降级成普通 transport close。

处理规则：

- 同入口第一次 M1/M4：立即在原入口重建 MUX；
- 同入口 60 秒内第二次 M1/M4：立即选择预排序中最好的其他入口重建；
- 超过 60 秒后再次发生：重新按第一次计算；
- 普通 MUX transport close、超时、主动关闭：不计入 M1/M4 streak，也不因此换入口；
- 没有可用备用入口：仍在原入口重建；
- 选中的备用入口无法建成完整 carrier 池：惩罚该入口，下一代 MUX 尝试下一名。

M1 与 M4 都属于数据完整性故障，在同一入口上的连续事件合并计数。

## 2. 入口评分

### 2.1 历史窗口

- 每个入口最多保存 60 次探测结果；正常 5 秒刷新时约覆盖 5 分钟。
- 成功 RTT 和成功/失败结果分别记录。
- 至少 6 个结果后视为具有基本置信度。
- `probe.ttl-seconds` 只控制结果新鲜期和失败惩罚时间，不再被误认为实际采样周期。

### 2.2 可靠性等级

排序首先比较可靠性：

| 等级 | 条件 |
|---|---|
| A | 样本充足，成功率 >= 98% |
| B | 样本充足，成功率 >= 90% |
| C | 样本少于 6，启动观察期 |
| D | 样本充足但成功率 < 90% |

当前不可达、结果过期或正在惩罚的入口不参与可用排序。

### 2.3 延迟风险

同一可靠性等级内按下式升序排列：

```text
risk = RTT_P50 + 1.5 * (RTT_P95 - RTT_P50) + 0.5 * MAD
```

样本不足的入口额外增加 100ms 置信度惩罚。可靠性优先于低 RTT，避免“延迟看起来低但经常失败”的入口胜出。

## 3. MUX 与乱序约束

- `compat`、`flow`、`balance`、`stripe` 都遵守“一代 MUX 单入口”。
- 多 carrier 仍可能因各 TCP 连接时延不同产生乱序；单入口只能消除跨入口时延差，不能消除同入口多 carrier 的乱序。
- 稳定优先建议使用 `compat + 1 carrier`。
- 需要吞吐时可评估 `balance + 2 carriers`；不建议稳定优先场景使用 `stripe`。
- 切换通过关闭旧 MUX generation、创建新 generation 完成，不让新旧入口同时承载同一代数据。

## 4. 配置语义

推荐配置：

```json
"client": {
    "probe": {
        "enabled": true,
        "timeout-ms": 800,
        "ttl-seconds": 30
    },
    "hot-switch": {
        "enabled": true
    }
}
```

`hot-switch.enabled=true` 现在只表示允许“连续 M1/M4 后的故障驱动 MUX 入口切换”。它不允许健康状态按质量切换。

以下字段继续解析以兼容旧配置，但不再触发健康会话迁移：

- `jitter-threshold-ms`
- `jitter-window`
- `weight-rtt`
- `switch-margin`
- `channels-per-entry`
- 原预热、观察、锁定和 drain 参数

主连接断线故障切换由 `client.servers + probe.enabled` 控制，不依赖质量热切换状态机。

## 5. 验收标准

1. 当前入口可用时，任意 RTT/抖动和评分变化都不会产生活动入口切换日志。
2. 主连接断线后，首个备用连接尝试立即开始。
3. 任意时刻只有一个 PPP 主握手在执行。
4. 同一 MUX generation 的全部 carrier 入口标签完全一致。
5. 同入口第一次 M1/M4 原地重建；60 秒内第二次切换到排序最优的其他入口。
6. 普通 MUX close 不增加 M1/M4 streak。
7. 备用入口建池失败后不会永久卡在该入口。
8. 新旧端都支持 `cmd_mux_rebuild` 时，服务端检测到的 M1/M4 也能传递给客户端切换状态机。
